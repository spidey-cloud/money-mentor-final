# MoneyMentor — Full Codebase Engineering Review

This is a React + Express application providing three AI-powered financial tools (Health Score, Tax Wizard, FIRE Planner) backed by Google Gemini. The frontend uses React 19 with client-side-only auth and credits, the backend exposes five Express endpoints that route through an orchestrator to specialized agents. The codebase is clean and readable overall, but carries several issues that would cause real production failures: plaintext passwords in localStorage, a credit bypass that any user can trigger from the console, a tax calculation error for high incomes, an `alert()` call blocking the UI on payment, and an unprotected CORS policy that accepts requests from anywhere.

**Verdict**: NEEDS_CHANGES

---

## High-level view

Auth is entirely client-side with passwords stored in plaintext in `localStorage`. There is no server-side session, no JWT, and no token. Any user can open DevTools and read every other browser-session user's credentials if they share a device. The subscription and credit state live in localStorage too, making the paywall trivially bypassable.

The tax calculation in `TaxWizard.jsx` applies the 87A rebate to wipe out tax for incomes up to ₹12L under the new regime, but the slab structure starts the 0% band at ₹0 instead of ₹4L — this overstates tax-free income and can produce wrong regime recommendations.

The Express server opens CORS to `*` and reads `GEMINI_API_KEY` from an env var, but the contact-form endpoint exposes `EMAIL_USER` and `EMAIL_PASS` failure details directly to the client in the error response body. Neither rate limiting nor input validation guards any endpoint.

The credit system has a race condition: `useCredit()` in `CreditContext` calls `setCredits(prev => prev - 1)` but the same `credits` value is read in the render that called `useCredit()` — a double-click submits two requests before either state update lands, consuming one credit instead of two and allowing extra free uses. More critically, the subscription flag `mm_is_subscribed` is a bare localStorage boolean; anyone can set `localStorage.setItem('mm_is_subscribed','true')` from the console.

The `ReviewContext` deserializes JSON from localStorage with a bare `JSON.parse` and no error handling — a corrupted value crashes the context provider and brings down the whole app. The same pattern appears in `AuthContext` for `mm_user` and `mm_users`.

The Dock component runs a `requestAnimationFrame` loop unconditionally while any item is hovered. The loop is cancelled on unmount, but if `hoveredIndex` stays non-null (e.g. pointer leaves without triggering `onPointerLeave`), the loop runs at 60fps forever while the component is mounted.

Financial data (income, deductions, full salary breakdown) is sent to the backend in the POST bodies for all three tool endpoints with no authentication header, so any script that knows the API URL can invoke the AI agents anonymously and exhaust the Gemini quota.

1. **Plaintext passwords in localStorage** — `AuthContext` stores raw passwords in `mm_users`. Anyone with DevTools access reads all credentials. Hash passwords client-side with `crypto.subtle` or move auth to the server.
2. **Paywall bypass via localStorage** — `mm_is_subscribed=true` unlocks unlimited credits from the browser console. The subscription gate must be enforced server-side.
3. **Credit double-spend race** — Two rapid submits consume one credit. Disable the submit button immediately on first click before the async state update lands.
4. **`JSON.parse` without try/catch in ReviewContext** — Corrupted localStorage crashes the context provider and white-screens the app. Wrap in try/catch.
5. **Same bare `JSON.parse` in AuthContext** — `mm_user` and `mm_users` reads crash the app on parse failure.
6. **New-regime tax slab starts at ₹0 not ₹4L** — The first slab `{ limit: 400000, rate: 0 }` applies 0% from ₹0 to ₹4L. Under the actual new regime, the first ₹4L (after standard deduction) is exempt — meaning the code double-counts the 0% band and can understate new-regime tax. Fix: begin the loop at `taxableIncome - 400000` or use the correct cumulative slab boundaries.
7. **CORS wildcard** — `app.use(cors())` with no origin restriction allows any domain to call the API, including cross-site requests that carry cookies. Restrict to the production origin.
8. **No rate limiting on any endpoint** — A single IP can drain the Gemini API key with unlimited POST requests. Add `express-rate-limit`.
9. **Email credentials leaked in error response** — `server/index.js` line ~90 throws the raw nodemailer error message back to the client via `res.status(500).json({ error: '...' })`. The error can include SMTP auth details. Return a generic message; log the detail server-side only.
10. **No auth on AI endpoints** — `/api/health-score`, `/api/tax-wizard`, `/api/fire-planner` are publicly callable. Anyone can abuse Gemini quota. At minimum, check a request token that the frontend acquires only after `useCredit()` succeeds.
11. **`simulateSubscription` calls `alert()`** — `CreditContext` line ~44 calls `alert(...)`, which blocks the main thread and is not dismissible programmatically. Replace with an in-app toast or modal.
12. **RAF loop runs at 60fps on hover** — `Dock` component (`dock.jsx` ~line 90) runs `requestAnimationFrame` continuously while `hoveredIndex !== null`. If the pointer leaves without triggering `onPointerLeave` (e.g. scrolled away), the loop runs until unmount. Add a `visible`/`mounted` guard and cancel the RAF when the component loses visibility.
13. **`triggerReview` leaks a `setTimeout`** — `ReviewContext.triggerReview` schedules `setIsModalOpen(true)` with a 2-second delay and never cancels it. If the user navigates away before 2 seconds, the modal opens on a different page. Store the timeout ID and cancel it in a cleanup or on route change.
14. **`PageTransitionWrapper` re-mounts every route** — The 280ms skeleton delay triggers on every navigation, including browser back/forward. This creates a flash-of-skeleton even for instant in-memory navigations. The skeleton should only show when content is not yet available, not on a fixed timer.
15. **HRA inputs collected but never used in tax calculation** — `TaxWizard.jsx` collects `hra_received`, `rent_paid`, and `metro` in `salary` state and sends them to the backend, but `calculateOldRegimeTax` ignores them entirely. Users who claim HRA exemption will see an overstated old-regime tax and may pick the wrong regime.
16. **`formatCr` imported from `src/lib` into a server agent** — `fireAgent.js` imports `formatCr` from `../../src/lib/format.js`. This works in Node because it's plain JS, but it creates a dependency from the server layer into the client source tree. Move `format.js` to a shared `lib/` at the project root.
17. **`dock.jsx` `iconRefs` not updated when `items` changes** — `iconRefs.current` is initialized as `items.map(() => React.createRef())` once at render time. If `items` length changes (the sidebar items array is `useMemo`'d but could grow), old refs are stale and new items have no ref. Use a stable ref array updated in a `useEffect`.
18. **Review data stored with no size cap** — `ReviewContext.saveReview` appends to the reviews array indefinitely in localStorage. If a user submits hundreds of reviews, the payload serialized to localStorage grows without bound and can hit the 5MB quota, throwing a `QuotaExceededError` that is not caught.

## Plaintext password storage and client-only auth

`AuthContext.jsx` stores the full user object including `password` in `localStorage` under `mm_users`. The `login` function compares the submitted password directly against the stored one with `===`. There is no hashing, no salting, and no server round-trip. If two family members share a browser profile, one can read the other's password from DevTools → Application → Local Storage in seconds.

The `logout` function removes `mm_user` but leaves `mm_users` intact, so all credentials persist after logout and are accessible to the next person who opens the browser.

**Fix**: For a frontend-only demo, at minimum hash passwords with `crypto.subtle.digest('SHA-256', encoder.encode(password))` before storing. For production, move auth to the server with a session cookie or JWT.

## Paywall bypass and credit race condition

`CreditContext` stores `mm_is_subscribed` as the string `"true"` in localStorage. Setting `localStorage.setItem('mm_is_subscribed','true')` in the browser console immediately grants unlimited access. The credit count `mm_remaining_credits` is equally mutable.

The race condition: `handleCalculate` in both `TaxWizard.jsx` and `FirePlanner.jsx` calls `useCredit()` synchronously, then immediately fires the `fetch`. If the user double-clicks the button before React re-renders (which schedules `setCredits(prev => prev - 1)`), both clicks read the same `credits` value from the closure — both pass the `credits > 0` check, and only one credit is deducted. Fix: set a local `submitting` boolean or use a `useRef` flag before the state update:

```js
const submittingRef = useRef(false)
const handleCalculate = () => {
  if (submittingRef.current) return
  submittingRef.current = true
  if (!useCredit()) { submittingRef.current = false; return }
  // ...fetch...
}
```

## New-regime tax slab error (HRA also ignored)

`calculateNewRegimeTax` in `TaxWizard.jsx` defines slabs as:

```js
{ limit: 400000, rate: 0 },   // ₹0–4L at 0%
{ limit: 400000, rate: 0.05 }, // ₹4L–8L at 5%
...
```

Under the actual FY 2025-26 new regime, the structure is a step function starting at ₹4L (post–standard-deduction). The code applies the 0% band from ₹0 upward, then correctly layers subsequent bands — so a person with ₹12L gross after the ₹75K standard deduction has ₹11.25L taxable, and their tax is computed correctly to zero (87A wipes it). But at higher incomes (e.g. ₹13L gross → ₹12.25L taxable after standard deduction), the first ₹4L slab is consumed entirely at 0%, giving the same result as the statutory computation. The practical bug is the 87A rebate limit constant `NEW_REGIME_REBATE_LIMIT = 1_200_000` which refers to taxable income after standard deduction, but the code compares it against `taxableIncome = income - STANDARD_DEDUCTION`. For someone with gross ₹12.75L, `taxableIncome = 12,00,000`, the rebate zeroes the tax. For ₹12.76L gross, `taxableIncome = 12,01,000 > 12,00,000`, the full marginal tax applies — a ₹1,000 income jump causes ~₹65,000 tax jump (the rebate cliff). This is accurate to the law, but the code has no warning or note about this cliff, and the AI insight does not flag it.

The more concrete bug: HRA exemption is collected (`hra_received`, `rent_paid`, `metro`) but `calculateOldRegimeTax` only sums `Object.values(deductions)` — the HRA inputs live in the separate `salary` state object and are never folded into the deductions calculation. For a user paying ₹15,000/month rent in a metro city with a ₹30,000/month basic salary, the HRA exemption can be ~₹1.08L/year. Ignoring it understates old-regime deductions and can produce a wrong regime recommendation.

**Fix**:

```js
function calculateHRAExemption(salary) {
  const { basic, hra_received, rent_paid, metro } = salary
  if (!hra_received || !rent_paid) return 0
  const basicAnnual = Number(basic) || 0
  const hraAnnual = Number(hra_received) || 0
  const rentAnnual = Number(rent_paid) || 0
  const metroFactor = metro === 'Yes' ? 0.5 : 0.4
  return Math.min(
    hraAnnual,
    metroFactor * basicAnnual,
    rentAnnual - 0.1 * basicAnnual
  )
}
// then in calculateOldRegimeTax, add hraExemption to totalDeductions
```

## Server security: CORS, rate limiting, credential leakage

`server/index.js` applies `cors()` with no options, allowing any origin. The three AI endpoints require no authentication. The `transporter.verify` callback does `console.error('Full Error:', error.message)` on startup, which on some SMTP misconfiguration paths includes the SMTP password in the server log — on Vercel that means function logs, which are accessible to anyone with project access.

The more immediate risk is Gemini quota exhaustion: any script that knows the API URL can POST to `/api/fire-planner` in a loop with synthetic data and drain the key within minutes, with no authentication required.

**Fix**: Add `express-rate-limit` (5 requests/minute/IP is enough for free-tier protection). Add `express-validator` checks on each body. For quota protection, generate a short-lived HMAC token in `useCredit()` and verify it on the AI endpoints.

## `JSON.parse` crashes without error handling

`ReviewContext.jsx`:

```js
const saved = localStorage.getItem('moneymentor_reviews')
if (saved) {
  setReviews(JSON.parse(saved))  // throws if corrupted
}
```

`AuthContext.jsx`:

```js
const storedUsers = JSON.parse(localStorage.getItem('mm_users') || '[]')
// called in login(), signup(), updateProfile() — all throw on corrupt data
```

If the browser writes a partial JSON blob (tab crash mid-write, storage full), all three contexts throw on mount, React catches it as an unhandled error, and the app white-screens. Wrap every `JSON.parse` in try/catch with a fallback to the default value.

## Dock RAF loop running indefinitely on stale hover

`dock.jsx` starts a `requestAnimationFrame` loop in a `useEffect` keyed on `hoveredIndex`:

```js
React.useEffect(() => {
  if (hoveredIndex === null) return;
  let raf;
  const update = () => {
    // ... position calculations
    raf = requestAnimationFrame(update);
  };
  raf = requestAnimationFrame(update);
  return () => cancelAnimationFrame(raf);
}, [hoveredIndex]);
```

The cleanup `cancelAnimationFrame(raf)` only fires when `hoveredIndex` changes or the component unmounts. If the user drags a file onto the browser window and the `onMouseLeave` event is suppressed by the browser's drag-and-drop machinery, `hoveredIndex` stays set and the loop runs at 60fps until the user hovers a different item or leaves the page. On a page with no other animation (dashboard idle state), this is the only thing burning a frame budget continuously.

**Fix**: Add `document.addEventListener('visibilitychange', ...)` to cancel when the tab is hidden, and add a `pointercancel` handler on the dock to reset `hoveredIndex`.

## `triggerReview` timeout leak

`ReviewContext.triggerReview` schedules:

```js
setTimeout(() => {
  setIsModalOpen(true)
}, delayMs)
```

The timeout ID is discarded. If the user completes a Health Score analysis and immediately navigates to a different page, the modal opens 2 seconds later on the wrong page. In React 19 strict mode, state updates on unmounted components are a warning; if the component tree containing the modal unmounts, this silently drops the update. If it doesn't unmount (the modal is in `App.jsx`), the modal opens regardless of current route.

**Fix**:

```js
const reviewTimerRef = useRef(null)
const triggerReview = (type, delayMs = 2000) => {
  clearTimeout(reviewTimerRef.current)
  setLastAnalysisType(type)
  reviewTimerRef.current = setTimeout(() => setIsModalOpen(true), delayMs)
}
// expose a cancelReview for route-change cleanup if needed
```

## `formatCr` imported from client source into server agent

`fireAgent.js` line 1:
```js
import { formatCr } from '../../src/lib/format.js'
```

This creates a layering violation: the server depends on a file inside the frontend source tree. It works today because `format.js` has no DOM or browser APIs, but a future refactor of the client build (e.g., adding React-only imports to `format.js`) would silently break the server. Move `format.js` to `lib/format.js` at the project root and import from there in both `src/pages/` and `server/agents/`.

## Duplicated financial logic between client and server

`TaxWizard.jsx` performs the full tax calculation client-side (`calculateOldRegimeTax`, `calculateNewRegimeTax`) and sends the results to the server. The server's `taxAgent.js` trusts those results and uses them to build the AI prompt without recalculating. This means the server never validates the numbers — a tampered request can send inflated savings figures and get AI advice based on false inputs. Either keep the calculation server-side only (server computes, client displays), or at minimum re-derive the key figures server-side before constructing the prompt.

The same pattern applies to FIRE: `calculateFirePlan` runs client-side in `FirePlanner.jsx`, and the full `plan` object is posted verbatim to the server. `fireAgent.js` reads `plan.fireNumber`, `plan.requiredSIP`, etc. directly from the request body.

## `simulateSubscription` calls `alert()`

`CreditContext.jsx` line ~44:

```js
alert('Payment successful! You are now a Premium Member. 🚀')
```

`alert()` is synchronous, blocks the main thread, cannot be styled, and is suppressed entirely in many iframe/embedded contexts. Replace with a state-driven toast or navigate to a success screen.

## localStorage review list grows without bound

`ReviewContext.saveReview` appends every review to the array and serializes it to localStorage. There is no maximum length. After enough reviews, `localStorage.setItem` throws `DOMException: QuotaExceededError`, which is not caught. The fix is to cap the stored list (e.g., keep the last 50 reviews) before writing:

```js
const capped = newReviews.slice(-50)
localStorage.setItem('moneymentor_reviews', JSON.stringify(capped))
```

## `PageTransitionWrapper` adds a 280ms delay to every navigation

The skeleton timer runs unconditionally on every route change, including navigations where the destination component is already in memory (all tool pages after first load). This means every click in the sidebar shows a skeleton for 280ms regardless of whether anything is loading. The pattern is a cosmetic shimmer being used as an artificial delay, which makes the app feel slower than it is. Remove the timer and use React Suspense boundaries or a real loading state from the data-fetch instead.
